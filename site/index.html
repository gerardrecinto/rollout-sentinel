How it works

A canary should be judged against the version it replaces, not only against fixed limits.

1

Five gates

Error rate, error rate against baseline, p99 latency, latency drift and CPU or memory saturation. Any breach halts the rollout and rolls back.

2

Warn is not breach

Latency drift over 30% or high CPU holds traffic at the current weight. Memory over its limit, or an unhealthy pod, is a breach.

3

Name the failure fast

A rule classifier reads pod reason, exit code, logs and events and labels OOMKilled, image pull, probe, config, database, network and crash loops.

Run it

Go 1.23 or later. The CLI uses the same mocks as this page until you wire it to Prometheus and a cluster.

git clone https://github.com/gerardrecinto/rollout-sentinel
cd rollout-sentinel
go build -o rollout-sentinel ./cmd/sentinel

./rollout-sentinel monitor --service retail-checkout-api
./rollout-sentinel triage --reason OOMKilled --exit-code 137
go test ./...

See the README for the Kubernetes and Prometheus wiring and the deploy manifests.

What this does not do
  • The metrics and cluster in this page are simulated. The repo's CLI demo also runs on mocks.
  • The classifier is regular expressions on text. A message it does not know comes back as an unknown anomaly at 40% confidence.
  • The ramp button scales metrics linearly with traffic weight to show the gate order. Real services do not degrade that smoothly.
